# Chapter 1: FENRIR

*Perturb the write address so a two-hop chain can form on its own.*

FENRIR stands for **Fast-weight Eager N-hop Recurrence for Inference and
Retrieval**. ("Eager" is the technical word for the lookup that happens at write
time; the rest of this README explains it in plain terms.)

This is the chapter write-up. For the big picture and how it connects to
chapter 2 (FREKI), see the [top-level README](../README.md). For the formal
version, see the short paper in [`paper/`](paper/) (the compiled PDF is
`paper/main.pdf`).

## The one-paragraph idea

FENRIR is a fast-weight mixer: a layer that keeps a small matrix `M`, writes
key/value pairs into it as it reads, and pulls values back out with a query. The
one twist is where a new memory gets filed. Instead of filing it under its own
key `k`, FENRIR first looks that key up in the memory it already has and files
the new memory under `k` plus what came back. The write address becomes
`k_eff = k + (lookup of k in M)`. The bet is that this small self-referential
step lets a two-hop chain assemble itself while the layer writes, with no extra
supervision.

## What I found

The task is a synthetic two-hop lookup. The model reads a batch of "key points
to bridge" facts and a batch of "bridge points to value" facts, then gets a query
and has to follow the chain to the right value. There are four candidate values,
so blind guessing scores 25% (this is the "chance floor" I compare against).

Three findings, all reproducible from the saved files in `outputs/`:

1. **The chain can form, but formation is a coin flip.** Good runs reach about
   92% to 94% on the full four-link ladder. But across random seeds, only about
   half the runs get there and the rest stall at the 25% floor. Concretely, for
   the `rev` operator: **5 of 10** seeds pass under the mixed-order training
   schedule, **6 of 10** under the joint schedule. The `fwd` operator almost
   never forms it: **0 of 5** mixed, **1 of 5** joint. I report both operators
   side by side rather than cherry-picking the winner.

2. **The self-referential term is the mechanism, not a garnish.** On a trained,
   working model, switching the `k + M·k` term off at test time collapses accuracy
   from about 96% to about 3% (worse than guessing). Switching it off during
   training means no seed ever learns the task (best run reaches 50% on the
   easiest link and never finishes the chain). This is a causal test: the term is
   the pathway the model routes the answer through.

3. **In the runs that work, the answer is localizable.** A simple linear probe
   reads the answer out of the third layer's state at roughly the model's own
   accuracy (0.90 and up) in passing seeds, and finds nothing (about 0.25, pure
   chance) at every layer in failing seeds.

**The honest headline:** the two-hop wall here is a *formation* problem, not an
*expressivity* problem. The layer is perfectly able to represent the chain; the
hard part is getting training to reliably discover it. The paper makes no claim
of a new primitive. Its contribution is this mechanistic characterization plus a
reproduction workflow you can audit line by line.

## The two operator variants

FENRIR's extra lookup can point in two directions. Both are shipped and compared
head to head:

| Variant | Extra term        | What the lookup does                                        |
|---------|-------------------|-------------------------------------------------------------|
| `fwd`   | `k_eff = k + Mᵀk` | Match the key against stored keys, return stored values.    |
| `rev`   | `k_eff = k + Mk`  | Match the key against stored values, return stored keys.    |

Both share the same write (`M += β · outer(k_eff, v)`) and the same read
(`y = Mᵀq`). Empirically `rev` is the one that forms the chain with any
regularity; `fwd` mostly does not. That asymmetry is a real finding, not a
labelling accident, and `tests/test_conventions.py` pins down exactly which
operator each name refers to.

## Reproduce

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt

pytest tests/                                 # audit tests must pass first (42 checks)
python train.py --variant rev --seed 0 --K1 4 # one training run
python eval.py  --ckpt outputs/<name>.ckpt    # the four-link accuracy ladder
bash scripts/reproduce_all.sh                 # every paper number, end to end
```

`scripts/reproduce_all.sh` runs, in order: the audit tests, the seed ladder
(Table 1), the mechanism probes (Table 2), and the depth-generalization eval
(Table 3). Every number the paper prints reads from a JSON file in `outputs/`,
which is committed, so you can check the paper against the data without running a
single GPU hour. (The training checkpoints themselves are not committed; they are
hundreds of megabytes and fully regenerated by the scripts.)

## Layout

```
model.py               the FENRIR mixer (fwd and rev variants), scaffold, stack
chunked.py             chunk-parallel kernel for the rev variant
tasks.py               the deterministic two-hop chain task samplers
train.py               single-checkpoint training (AdamW, bf16 on CUDA)
eval.py                the multi-hop accuracy ladder, JSON output
probe_f3/f4/f5.py      the mechanism probes (logit lens, mid-scan, alignment)
eval_eager_knockout.py the switch-it-off-at-test-time causal check
scripts/               reproduce_all.sh and the per-table runners
tests/                 audit-as-code: every convention the paper relies on
outputs/               committed result JSONs (the paper's numbers) + AGGREGATE.md
paper/                 the compiled short paper (PDF) and its LaTeX source
```

## A note on the audit tests

Every convention the paper depends on (which way `M` stores its keys and values,
which operator each variant name means, which direction the read runs) is checked
by a test in `tests/`. The passing tests *are* the audit. If a later edit
silently flips a convention, a test breaks. That is the whole point: the claims
and the code cannot drift apart without something going red.

## Reproducibility notes

Runs use deterministic PyTorch operations where they exist. Seeds control both
model initialization and data sampling. Exact numbers vary a little across
hardware (bf16 plus non-associative reductions are not bit-identical), but
accuracy holds within seed-to-seed noise. Reference hardware: NVIDIA RTX 5090.

One cross-reference to head off confusion: the paper's abstract mentions a
six-hop result "under a training-time filler recipe." That filler recipe is
chapter 3 of this repo (see [`../filler/`](../filler/)); everything in *this*
chapter is the baseline recipe.
